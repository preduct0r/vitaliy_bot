# Telegram-аватар Виталия

Локальный bot-сервис для репетиции сложной встречи. Он работает только на Mac:
Telegram получает материалы, а локальный `codex exec` использует уже сохранённую
авторизацию ChatGPT. На сервер `tof` токен Telegram и авторизация ChatGPT не
переносятся.

Бот — симулятор переговорного паттерна, а не настоящий Виталий. Профиль
`v1.1.0` использует двенадцать подтверждённых пользователем записей, не содержит дословных реплик и
не включает Виталия Муймапова, вероятные встречи 02.07 и 23.07 или дубли 29.06
и 18.08. Две новые записи от 15.09.2026 доступны в `discussions/vitaly/` вместе с
описанием качества источников. Профиль v1.0.0 сохранён для исторического сравнения.

## Настройка на Mac

Создать бота через BotFather и сохранить токен вне репозитория в
`~/Library/Application Support/TOF Vitaly Bot/config.env`:

```dotenv
VITALY_BOT_TOKEN=...
VITALY_BOT_CODEX_BIN=/Applications/ChatGPT.app/Contents/Resources/codex
VITALY_BOT_MODEL=gpt-6.1-sol
VITALY_BOT_REASONING_EFFORT=high
VITALY_BOT_MODEL_TIMEOUT_SECONDS=480
VITALY_BOT_EVIDENCE_TIMEOUT_SECONDS=180
VITALY_BOT_CONTEXT_TTL_DAYS=4
# Необязательно: по умолчанию <STATE_DIR>/knowledge, вне Git и release-каталогов.
VITALY_BOT_KNOWLEDGE_DIR="~/Library/Application Support/TOF Vitaly Bot/knowledge"
# Отклонять новую загрузку до записи, если свободного места меньше порога.
VITALY_BOT_MIN_FREE_BYTES=2147483648
# Час автоматического цикла по локальному времени Mac. По умолчанию — 04:00.
VITALY_BOT_LEARNING_RUN_HOUR=4
# Только локально назначенные Telegram user_id могут остановить/откатить автообновление.
VITALY_BOT_OPERATOR_USER_IDS=123456789
```

Проверить авторизацию (токен Telegram для этой проверки ещё не нужен) и вручную
запустить polling:

```zsh
.venv/bin/python scripts/run_vitaly_bot.py --check-auth
.venv/bin/python scripts/run_vitaly_bot.py
```

Для автозапуска сначала посмотреть plist, затем установить его. Токен в plist не
попадает: там хранится только путь к локальному `config.env`.

```zsh
.venv/bin/python scripts/install_vitaly_bot_launch_agent.py \
  --env-file "$HOME/Library/Application Support/TOF Vitaly Bot/config.env" --dry-run
.venv/bin/python scripts/install_vitaly_bot_launch_agent.py \
  --env-file "$HOME/Library/Application Support/TOF Vitaly Bot/config.env" --load
```

`--load` полностью перезагружает уже работающий job, поэтому обновляет и его
`PATH`; повторите эту команду после изменения launchd-настроек.

`launchd` запускает один polling-процесс. Логи: `~/Library/Logs/TOF-Vitaly-Bot/`.
Исходные и производные файлы кейсов, транскриптов, рендеров и evidence-пакетов
сохраняются бессрочно вне Git. Автоматической 30-дневной очистки больше нет;
при недостатке свободного места новая загрузка отклоняется с понятным сообщением.

Один запуск модели по умолчанию ограничен восемью минутами. По истечении этого
срока бот останавливает всю группу процессов Codex, включая дочерние, записывает
код ошибки в `/status` и может сделать единственную повторную попытку для
временного сбоя. Лимит меняется только локально через
`VITALY_BOT_MODEL_TIMEOUT_SECONDS`.

Если кейс не закрыли `/stop` и им не пользовались больше четырёх суток, при следующем
сообщении бот явно сообщает о сбросе и создаёт новый пустой кейс. Ранее загруженные
файлы остаются в локальном архиве, но больше не участвуют в аудите или
репетиции. Срок можно поменять локальной переменной
`VITALY_BOT_CONTEXT_TTL_DAYS`.

## Пользовательский сценарий

`/new` создаёт независимый кейс. Можно прислать до десяти файлов (PPTX, PDF,
DOCX, XLSX, TXT, MD, CSV, PNG или JPEG) по 50 МБ, либо обычный текст. Общий
предел — 200 страниц, слайдов или листов. Бот принимает работу только в
личном чате Telegram: в группах он явно отказывает, чтобы кейсы, материалы и
обратная связь разных людей никогда не оказались в общем контексте.

- `/review` ставит полный аудит в общую FIFO-очередь.
- `/grill` начинает конечную репетицию; следующий текст считается единственным ответом на вопрос.
- `/stop` сразу прекращает выдачу вопросов и формирует итог по завершённым ответам. Если ответа ещё не было, просто завершает репетицию.
- `/status` показывает кейс, этап, очередь, длительность и последнюю ошибку.
- `/meeting` сразу предлагает отправить текст, TXT, MD, DOCX или текстовый PDF.
  По умолчанию берётся текущая дата Mac; кнопка «Изменить дату» — опциональна.
  Название извлекается из заголовка записи или берётся из имени файла. Архив
  отдельный от текущего кейса и не сбрасывает его аудит.
- `/learning` показывает активную версию знаний, безопасное описание последнего
  изменения по типам обновления и только собственные отправки пользователя.
  Чужие транскрипты, фидбек, названия документов и их факты не показываются.
- `/cancel` отменяет ожидающий текст общей обратной связи или незавершённую
  загрузку встречи.

Когда бот занят загрузкой, обработкой материалов, проверкой ledger или модельным
запуском, он редактирует одно статусное сообщение и показывает Telegram-индикатор
`typing`. Новые файлы, текст и команды в этот момент отклоняются до записи в
кейс или очередь; доступны `/status` и `/stop` для уже начатой репетиции. Поле
ввода Telegram отключить нельзя, поэтому это функциональная, а не клиентская
блокировка. Повторная команда не создаёт второй job.

Для аудита и репетиции бот один раз на кейс собирает evidence-пакет на сервере
`tof`. Версионируемый read-only скрипт передаётся по SSH и читает только
`/srv/tof/state/current_generation.json` и опубликованный ledger. Точные
идентификаторы ищутся потоковой SQL-выборкой DuckDB без загрузки многогигабайтных
CSV целиком; ответы содержат ID поколения и `source_document_id`. Источники
`needs_review` исключаются. Если текущий `tof` недоступен или факт не подтверждён,
бот сообщает об этом и не подменяет его локальными либо старыми данными.

Одновременно выполняется ровно один модельный запрос для всех пользователей.
Это не квота и не ограничение доступа: бот открыт, но защищает локальную
авторизацию от конкурирующих процессов. При исчерпании ChatGPT-подписки или
потере авторизации бот сообщает точную причину.

## Проверка профиля

В профиле 31.07 и 18.08 оставлены holdout-встречами. После первого реального
аудита сохранить его структурированный JSON и выполнить:

```zsh
.venv/bin/python scripts/evaluate_vitaly_profile_holdout.py --predicted review.json
```

Среди первых десяти `topic` должно совпасть не менее 70% размеченных тем
holdout: периметр и источник цифр, измеримость эффекта, владелец и срок,
приоритет и готовность внедрения.

## Исправление одного пункта

Под аудитом нажмите «Исправить пункт», выберите G (пробел), C (противоречие)
или Q (вопрос), затем объясните ошибку. Номер пункта постоянный. Можно указать
название файла и номер слайда; бот перечитает исходный фрагмент и его рендер.
Результат: исправлено, снято, оставлено в силе или нужно уточнение. Пояснение не
становится новым документом. При уточнении ответьте следующим сообщением.
«Отмена» завершает выбор без изменения отчёта. Во время репетиции сначала `/stop`.

«Актуальный отчёт» читает сохранённую версию без модели. Общий балл, вердикт,
список подготовки и остальные пункты не пересчитываются; снятые пункты помечены.
Исправления учитываются при следующей репетиции, зависимые вопросы пропускаются.
Если все вопросы сняты, бот сообщает об этом. Для старых отчётов вызов `/review`
возвращает кэшированный отчёт с кнопками, без повторного аудита.

История хранится в добавочных SQLite-таблицах `audit_versions`, `audit_corrections`
и `audit_messages`. Исходный `cases.review_json` не переписывается — это позволяет
вернуть старый код без отката базы. Непринятые гипотезы не становятся общей памятью.
Новый материал инвалидирует аудит; старые кнопки и старый кейс не принимают правки.

## Накопительное улучшение

Под отчётом есть отдельная кнопка «Общая обратная связь». Следующее сообщение
сохраняется как пояснение, а не как материал или ответ на репетиции. Модель
сверяет его с исходным отчётом и основаниями и сообщает один из результатов:
«учтено только в этом кейсе», «добавлено в проверочные примеры», «включено в
общие правила» или «недостаточно оснований». Само возражение не считается
доказательством ошибки. Точечные исправления G/C/Q также сохраняются как
проверочные примеры, только если пункт снят или исправлен.

`/meeting` хранит загрузку в `VITALY_BOT_KNOWLEDGE_DIR` и проверяет точный хэш
до модельного запуска; содержательные дубли и продолжения сверяются по
нормализованному тексту и метаданным. В транскриптах Granola без надёжных меток
говорящих роль Виталия выводится по очереди вопросов и ответов и сравнению с
подтверждённым профилем. Если отдельные реплики всё ещё нельзя разделить,
запись принимается целиком с пониженной уверенностью; другим Виталием она
считается только при явном свидетельстве в тексте. Аудио и распознавание речи
не входят в этот интерфейс. Незавершённая загрузка переживает перезапуск; для
изменения даты можно вернуться к отправке транскрипта без отмены встречи.
Текст транскрипта для классификации и обучения читается полностью. Слишком
большой контекст не отправляется частично: задача сообщает об ограничении и
сохраняет исходник.

Фоновое обновление запускается один раз в сутки в 04:00 по локальному времени
Mac и только когда нет пользовательских jobs, включая ожидающие разборы
обратной связи и встреч. Если очередь занята в это часовое окно, дневного
догоняющего запуска не будет: цикл подождёт до 04:00 следующего дня.
Уже запущенный модельный вызов может штатно закончиться после 04:59, но
следующий автоматический шаг (включая проверку кандидата) ждёт следующего
утра. При перезапуске незавершённая фоновая задача также ждёт следующего окна.
Оно использует один и тот же единственный модельный
процесс: после каждого модельного шага очередь снова отдаёт приоритет людям.
За один цикл берётся не более восьми источников и 100 000 символов; оставшиеся
источники остаются в очереди следующего цикла. Это не обрезает архив и не
смешивает его с контекстом кейса.
Генератор предлагает только ограниченный JSON-патч, а независимый проверяющий
получает источники и критерии, но не рассуждения генератора. Узкое правило
аудита требует подтверждённого источника; широкий паттерн поведения — минимум
две независимые принятые встречи.

Подробный текст кандидатного правила и пересказ новой встречи остаются только в
архиве. Для нового кейса разрешён лишь закрытый каталог универсальных проверок
(определение/период/единицы/подпись изображения/источник цифры/владелец и
внедрение) и безопасные режимы жёсткости вопроса. Поэтому один пользовательский
документ не может стать фактом или скрытой инструкцией для другого пользователя.

Перед включением кандидат проходит неизменяемый набор из 13 синтетических
регрессионных сценариев: ложное и настоящее противоречия, периоды, единицы,
подписи изображений, неподтверждённые числа, владелец и срок, механизм
внедрения, неоднозначный говорящий и покрытие стиля. Новый пакет включается
атомарно только если все обязательные сценарии проходят, новых критических
ошибок нет, улучшен хотя бы один целевой сценарий и покрытие тематических групп
среди первых десяти вопросов не ниже 70% и не хуже текущего. При ничьей,
конфликте или ошибке остаётся предыдущая версия.

Пакет знаний закрепляется за новым кейсом в момент его создания. Старый аудит,
правки и репетиция продолжают использовать прежний пакет и никогда не
перегенерируются автоматически. Локально назначенные операторы могут выполнить
`/learning_pause`, `/learning_resume` и `/learning_rollback <package-id>`;
пустой список `VITALY_BOT_OPERATOR_USER_IDS` закрывает эти команды для всех.
История пакетов, решений, хэшей, model-run и событий остаётся в SQLite; тексты
не дублируются в технических логах.

### Локальный архив и операционный просмотр

По умолчанию состояние находится в
`~/Library/Application Support/TOF Vitaly Bot/`: кейсы — в `cases/`, архив
встреч и производные файлы — в `knowledge/`, индекс и телеметрия — в
`vitaly_bot.sqlite3`. Каталог `knowledge/` можно перенести только локальной
настройкой `VITALY_BOT_KNOWLEDGE_DIR`; он не должен лежать в Git или каталоге
release. Архив хранится бессрочно: четырёхдневный сброс освобождает только
контекст кейса, но не удаляет его исходники.

Ниже — read-only запросы для локального оператора или другого локального
агента. Они показывают идентификаторы, статусы и основания, но не выводят
тексты документов, токен Telegram или содержимое `config.env`.

```zsh
bot_db="$HOME/Library/Application Support/TOF Vitaly Bot/vitaly_bot.sqlite3"

# Текущий и прежние пакеты знаний.
sqlite3 -readonly "$bot_db" '
  SELECT id, version, status, created_at, enabled_at, summary
  FROM knowledge_packages ORDER BY created_at DESC;'

# Кандидаты: область, ожидаемое улучшение, решение проверяющего и причина отказа.
sqlite3 -readonly "$bot_db" '
  SELECT id, status, scope, expected_improvement, package_id, error, generated_at, verified_at
  FROM learning_candidates ORDER BY generated_at DESC;'

# Ссылки на источники кандидата и результат регрессионного допуска.
sqlite3 -readonly "$bot_db" '
  SELECT c.id, c.source_ids_json, r.passing, r.created_at
  FROM learning_candidates AS c
  LEFT JOIN learning_regression_runs AS r ON r.candidate_id = c.id
  ORDER BY c.generated_at DESC, r.created_at DESC;'

# Недиагностические события: длительность, итог и безопасный код ошибки.
sqlite3 -readonly "$bot_db" '
  SELECT event_type, object_type, object_id, status, duration_ms, error_code, created_at
  FROM learning_events ORDER BY created_at DESC LIMIT 50;'
```

Управление автообновлением доступно только Telegram user ID из
`VITALY_BOT_OPERATOR_USER_IDS`: `/learning_pause`, `/learning_resume`,
`/learning_rollback <package-id>`. Сначала приостановьте автообновление,
проверьте нужный `package-id` read-only запросом, затем выполните откат.
Откат меняет пакет только для новых кейсов; открытые кейсы сохраняют закреплённую
версию. Если список операторов пуст, эти команды недоступны всем. Не отправляйте
токен или user ID в общий чат и не запускайте эти команды от имени пользователя.

## Выпуск и откат

GitHub: `git@github.com:preduct0r/vitaliy_bot.git`. Тег
`baseline-before-point-corrections` содержит исходную версию. `SOURCE.json`
сопоставляет экспорт с commit TOF; экспортируется явный список файлов командой
`scripts/export_vitaly_bot.py`, без пользовательских баз, загрузок и секретов.
Для серверной проверки нужны SSH-доступ к `tof` и DuckDB в
`/srv/tof/repos/tof_v1/.venv/bin/python`. Имя SSH-хоста можно переопределить
через `TOF_SSH_HOST`; локальный checkout TOF в маршруте проверки не участвует.

Рабочий код не редактируется во время разработки: используется отдельный worktree.
Резервные копии создаёт `scripts/vitaly_snapshot.py` через SQLite Backup, вместе
с деревом файлов, patch, конфигурацией и manifest SHA-256. Снимок файлов live-кейсов
фиксирует время копирования; база имеет транзакционно согласованное состояние.

Оба скрипта выпуска архивируют каталог знаний в `knowledge.tar.gz`, включая
случай, когда он вынесен из `STATE_DIR`. Путь выбирается в порядке
`--knowledge` → экспортированная `VITALY_BOT_KNOWLEDGE_DIR` → та же переменная
в локальном `config.env` (или `VITALY_BOT_ENV_FILE`) → `STATE_DIR/knowledge`.
Скрипты читают только значение пути, не печатают и не записывают токен в
консоль. Для нестандартного пути укажите его явно при снимке и выпуске:

```zsh
.venv/bin/python scripts/vitaly_snapshot.py \
  --root /absolute/path/to/tof_v1 --state "$HOME/Library/Application Support/TOF Vitaly Bot" \
  --knowledge "$HOME/Library/Application Support/TOF Vitaly Archive" \
  --destination /absolute/private/backup-directory

.venv/bin/python scripts/vitaly_release.py --candidate-plist /absolute/candidate.plist \
  --state "$HOME/Library/Application Support/TOF Vitaly Bot" \
  --knowledge "$HOME/Library/Application Support/TOF Vitaly Archive" \
  --backup /absolute/private/backup-directory
```

`scripts/vitaly_release.py --candidate-plist ... --state ... --backup ...`
переключает только свободный бот: проверяет очередь, загрузки и репетиции,
замораживает старый процесс для повторной проверки, сохраняет SQLite и plist,
завершает старый процесс и запускает новый. При занятом боте выпуск откладывается.
Проверяется устойчивый PID и целостность базы; ошибка запуска возвращает прежний plist.
Telegram updates не удаляются. Новая версия дожидается обработчиков при штатном
завершении и использует эксклюзивный локальный lock по Telegram-токену.

Откат выполняется той же командой, где `--candidate-plist` — сохранённый
`launchd.plist` предыдущего выпуска, а `--backup` — новый уникальный каталог.
Не восстанавливайте старую базу для штатного отката: текущая база содержит новые
