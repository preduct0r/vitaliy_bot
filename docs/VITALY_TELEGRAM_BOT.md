# Telegram-аватар Виталия

Локальный bot-сервис для репетиции сложной встречи. Он работает только на Mac:
Telegram получает материалы, а локальный `codex exec` использует уже сохранённую
авторизацию ChatGPT. На сервер `tof` токен Telegram и авторизация ChatGPT не
переносятся.

Бот — симулятор переговорного паттерна, а не настоящий Виталий. Профиль
`v1.1.0` использует двенадцать подтверждённых пользователем записей, не содержит дословных реплик и
не включает Виталия Муймапова, вероятные встречи 02.07 и 23.07 или дубли 29.06
и 18.08. Две новые записи от 15.09.2026 доступны в `discussions/vitaly/` вместе с
описанием качества источников. Профиль v1.0.0 сохранён для исторического сравнения.

## Настройка на Mac

Создать бота через BotFather и сохранить токен вне репозитория в
`~/Library/Application Support/TOF Vitaly Bot/config.env`:

```dotenv
VITALY_BOT_TOKEN=...
VITALY_BOT_CODEX_BIN=/Applications/ChatGPT.app/Contents/Resources/codex
VITALY_BOT_MODEL=gpt-6-astra
VITALY_BOT_REASONING_EFFORT=xhigh
VITALY_BOT_MODEL_TIMEOUT_SECONDS=480
VITALY_BOT_EVIDENCE_TIMEOUT_SECONDS=180
VITALY_BOT_CONTEXT_TTL_DAYS=4
```

Проверить авторизацию (токен Telegram для этой проверки ещё не нужен) и вручную
запустить polling:

```zsh
.venv/bin/python scripts/run_vitaly_bot.py --check-auth
.venv/bin/python scripts/run_vitaly_bot.py
```

Для автозапуска сначала посмотреть plist, затем установить его. Токен в plist не
попадает: там хранится только путь к локальному `config.env`.

```zsh
.venv/bin/python scripts/install_vitaly_bot_launch_agent.py \
  --env-file "$HOME/Library/Application Support/TOF Vitaly Bot/config.env" --dry-run
.venv/bin/python scripts/install_vitaly_bot_launch_agent.py \
  --env-file "$HOME/Library/Application Support/TOF Vitaly Bot/config.env" --load
```

`--load` полностью перезагружает уже работающий job, поэтому обновляет и его
`PATH`; повторите эту команду после изменения launchd-настроек.

`launchd` запускает один polling-процесс. Логи: `~/Library/Logs/TOF-Vitaly-Bot/`.
Исходные и производные файлы кейса очищаются через 30 дней; SQLite-метаданные и
диагностика остаются.

Один запуск модели по умолчанию ограничен восемью минутами. По истечении этого
срока бот останавливает всю группу процессов Codex, включая дочерние, записывает
код ошибки в `/status` и может сделать единственную повторную попытку для
временного сбоя. Лимит меняется только локально через
`VITALY_BOT_MODEL_TIMEOUT_SECONDS`.

Если кейс не закрыли `/stop` и им не пользовались больше четырёх суток, при следующем
сообщении бот явно сообщает о сбросе и создаёт новый пустой кейс. Ранее загруженные
файлы остаются только на хранении до 30-дневной очистки и больше не участвуют в
аудите или репетиции. Срок можно поменять локальной переменной
`VITALY_BOT_CONTEXT_TTL_DAYS`.

## Пользовательский сценарий

`/new` создаёт независимый кейс. Можно прислать до десяти файлов (PPTX, PDF,
DOCX, XLSX, TXT, MD, CSV, PNG или JPEG) по 50 МБ, либо обычный текст. Общий
предел — 200 страниц, слайдов или листов.

- `/review` ставит полный аудит в общую FIFO-очередь.
- `/grill` начинает конечную репетицию; следующий текст считается единственным ответом на вопрос.
- `/stop` сразу прекращает выдачу вопросов и формирует итог по завершённым ответам. Если ответа ещё не было, просто завершает репетицию.
- `/status` показывает кейс, этап, очередь, длительность и последнюю ошибку.

Когда бот занят загрузкой, обработкой материалов, проверкой ledger или модельным
запуском, он редактирует одно статусное сообщение и показывает Telegram-индикатор
`typing`. Новые файлы, текст и команды в этот момент отклоняются до записи в
кейс или очередь; доступны `/status` и `/stop` для уже начатой репетиции. Поле
ввода Telegram отключить нельзя, поэтому это функциональная, а не клиентская
блокировка. Повторная команда не создаёт второй job.

Для аудита и репетиции бот один раз на кейс собирает evidence-пакет через
персональное server workspace. Он читает только текущий опубликованный ledger
типизированными загрузчиками, сохраняет ID поколения и отбрасывает источники
`needs_review`. В пакет входят только точные совпадения идентификаторов из
материала. Если текущий `tof` недоступен или факт не подтверждён, бот честно
сообщает об этом и не подменяет его локальными либо старыми данными.

Одновременно выполняется ровно один модельный запрос для всех пользователей.
Это не квота и не ограничение доступа: бот открыт, но защищает локальную
авторизацию от конкурирующих процессов. При исчерпании ChatGPT-подписки или
потере авторизации бот сообщает точную причину.

## Проверка профиля

В профиле 31.07 и 18.08 оставлены holdout-встречами. После первого реального
аудита сохранить его структурированный JSON и выполнить:

```zsh
.venv/bin/python scripts/evaluate_vitaly_profile_holdout.py --predicted review.json
```

Среди первых десяти `topic` должно совпасть не менее 70% размеченных тем
holdout: периметр и источник цифр, измеримость эффекта, владелец и срок,
приоритет и готовность внедрения.

## Исправление одного пункта

Под аудитом нажмите «Исправить пункт», выберите G (пробел), C (противоречие)
или Q (вопрос), затем объясните ошибку. Номер пункта постоянный. Можно указать
название файла и номер слайда; бот перечитает исходный фрагмент и его рендер.
Результат: исправлено, снято, оставлено в силе или нужно уточнение. Пояснение не
становится новым документом. При уточнении ответьте следующим сообщением.
«Отмена» завершает выбор без изменения отчёта. Во время репетиции сначала `/stop`.

«Актуальный отчёт» читает сохранённую версию без модели. Общий балл, вердикт,
список подготовки и остальные пункты не пересчитываются; снятые пункты помечены.
Исправления учитываются при следующей репетиции, зависимые вопросы пропускаются.
Если все вопросы сняты, бот сообщает об этом. Для старых отчётов вызов `/review`
возвращает кэшированный отчёт с кнопками, без повторного аудита.

История хранится в добавочных SQLite-таблицах `audit_versions`, `audit_corrections`
и `audit_messages`. Исходный `cases.review_json` не переписывается — это позволяет
вернуть старый код без отката базы. Непринятые гипотезы не становятся общей памятью.
Новый материал инвалидирует аудит; старые кнопки и старый кейс не принимают правки.

## Выпуск и откат

GitHub: `git@github.com:preduct0r/vitaliy_bot.git`. Тег
`baseline-before-point-corrections` содержит исходную версию. `SOURCE.json`
сопоставляет экспорт с commit TOF; экспортируется явный список файлов командой
`scripts/export_vitaly_bot.py`, без пользовательских баз, загрузок и секретов.
Для отдельного checkout или каталога выпуска задайте окружение
`VITALY_BOT_TOF_ROOT` с абсолютным путём к настроенному клиенту TOF.

Рабочий код не редактируется во время разработки: используется отдельный worktree.
Резервные копии создаёт `scripts/vitaly_snapshot.py` через SQLite Backup, вместе
с деревом файлов, patch, конфигурацией и manifest SHA-256. Снимок файлов live-кейсов
фиксирует время копирования; база имеет транзакционно согласованное состояние.

`scripts/vitaly_release.py --candidate-plist ... --state ... --backup ...`
переключает только свободный бот: проверяет очередь, загрузки и репетиции,
замораживает старый процесс для повторной проверки, сохраняет SQLite и plist,
завершает старый процесс и запускает новый. При занятом боте выпуск откладывается.
Проверяется устойчивый PID и целостность базы; ошибка запуска возвращает прежний plist.
Telegram updates не удаляются. Новая версия дожидается обработчиков при штатном
завершении и использует эксклюзивный локальный lock по Telegram-токену.

Откат выполняется той же командой, где `--candidate-plist` — сохранённый
`launchd.plist` предыдущего выпуска, а `--backup` — новый уникальный каталог.
Не восстанавливайте старую базу для штатного отката: текущая база содержит новые
сообщения и совместима со старой версией. Старый код не показывает новые исправления,
но сохраняет их в добавочных таблицах. Восстановление повреждённой базы — отдельная
операция после сохранения её текущего состояния.
